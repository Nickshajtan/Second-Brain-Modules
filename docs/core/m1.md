# Core M1: committed knowledge foundation

The `second_brain_core` Python module implements creation and reads for private,
single-membership knowledge. It is a passive application boundary with no server,
reconciliation, governance engine or background execution. The original M1 scope below is extended by [M2.1 immutable history](m2-1-immutable-history.md) and the
[M2.1.1 disposable history projection](m2-1-1-history-hardening.md); this is not a search index. The existing
JSON Schema 2020-12 registry remains authoritative; no schema or generated files
were changed for M1.

## Composition and use

Use Python 3.12+, Git and the existing locked environment. Add `packages/python`
to the import path, as for the contract adapter. Initialize a **dedicated disposable
or explicitly provisioned backing Git repository** outside this reusable module.
Core does not initialize, checkout, reset or materialize a human vault.

```python
from pathlib import Path
from second_brain_contracts import ContractValidator
from second_brain_core import Core, GitStore, InstanceContext, TrustedPrincipal

# All identities and grants come from a trusted host/bootstrap, not request JSON.
principal = TrustedPrincipal(principal_id, frozenset({
    (cluster_id, "node.create"), (cluster_id, "membership.admit"),
    (cluster_id, "node.read"), (cluster_id, "relation.create"),
    (cluster_id, "relation.read"),
}), bootstrap=True)
context = InstanceContext(instance_id, Path(backing_repository),
                          "refs/heads/second-brain", principal)
contracts = ContractValidator()  # Or explicit verified contract bundle root.
core = Core(context, GitStore(context.repository, context.managed_ref), contracts)

# Once only: canonical Cluster / NodeTypeDefinition / RelationTypeDefinition
# payloads, plus local metadata schemas. See tests/test_core_m1.py for complete
# fabricated inputs; none of those fixture identities are deployment credentials.
core.bootstrap(bootstrap_records, metadata_schemas)

generation = core.generation()
receipt = core.execute(node_create, expected_generation=generation)
result = core.read(node_read)
wire = contracts.dump("transaction", result)
```

`execute` accepts generated `NodeCreate`/`RelationCreate`, decoded JSON, raw JSON
UTF-8 bytes or text. `submit` accepts the canonical generated `BatchRequest` or
those JSON forms. `read` accepts generated `NodeRead`/`RelationRead` or JSON.
Generated objects are serialized and canonically revalidated even when supplied
as already typed objects; Pydantic assignment or `model_construct` cannot bypass
ingress. Canonical parsing constructs the generated root model before business
checks. Generated objects and their canonical JSON wire views are used internally;
there is no handwritten domain DTO class. Results are generated
`CommittedReceipt`/`ReadResult`; `CoreError.error` is generated `DomainError`.
Outputs are canonically validated with `ContractValidator.parse`/`dump`.

The application composes explicit collaborators. `ContractBoundary` owns ingestion,
`AccessControl` owns permitted selection, `DomainRules` owns invariants,
`KnowledgeRepository` loads committed snapshots, and `ReceiptStore` owns replay.
`NodeCreateStrategy`/`RelationCreateStrategy` each prepare their resource changes,
verify their receipt result and reauthorize replay. Dedicated read strategies select
Node or Relation content. `Core` chooses these strategies from fixed operation maps
and owns the single writer/commit boundary. There is no dynamic strategy loader or
dependency injection framework. The Git adapter separates command execution, tree
construction, commit creation, ref publication and platform lock lifecycle.

## Supported semantics

- `node.create`: explicit optional `payload.node_id` is the allocated stable Node ID,
  distinct from request identity. New producers should allocate it before constructing
  the request. Legacy omission intentionally retains `request_id` allocation without
  rewriting persisted requests. In a batch, later Relations reference the allocated ID.
  New NodeRevision records retain exact immutable `snapshot` content and validate its
  digest. Legacy metadata-only revisions remain accepted; M2 requires explicit backfill.
  Node types/versions and metadata schemas must be registered at bootstrap;
  metadata, validity intervals, target Cluster and delegated initial admission
  are checked. Initial Node, NodeRevision and Membership are created together.
  NodeRevision and admission records bind the trusted creating principal.
- `relation.create`: an independent caller-allocated Relation UUID, one owner
  Cluster, initial revision 1, registered predicate/version and accessible existing
  endpoints. Endpoint type constraints, cross-instance references and self-link
  rules are checked. No inverse Relation or endpoint revision is created.
- Reads select one managed commit, validate its complete supported state and return
  only the requested Node or Relation. A Node selection may specify its sole
  Cluster and exact current RevisionRef; other selections fail concealed. A
  Relation requires its own read grant and read access to both endpoints.
- Explicit aggregate expectations check revision and optional digest against the
  selected state. The mandatory batch generation pins *all* registry, policy,
  admission and resource state. Unsupported operations reject the entire batch.
  No update/history operation is implemented; initial revisions are immutable.

Bootstrap only accepts canonical Cluster/type/predicate definitions. It requires
the trusted `bootstrap` binding, verifies Cluster ownership, permits private active
Clusters and creates the ref only if absent. Metadata schemas are local inline
Draft 2020-12 schemas, with supported formats and no `$ref`, dynamic reference,
resource ID or dialect override. This bounded M1 profile avoids online resolution.

## Authorization boundary

The host binds one immutable principal/grant snapshot to each Core. Grants name
an exact Cluster and supported action; absent grants deny. Replace the Core binding
when grants change; no caller request chooses its principal or Owner status.
There is no wildcard or implicit Owner bypass. Creating a Node requires both
`node.create` and `membership.admit`; a create grant does not imply a read grant.
Replay rechecks the original creation/admission grants and Relation endpoint reads.
Missing and inaccessible targets return the same sanitized `NOT_FOUND`.

M1 rejects shared/multi-membership state instead of resolving O4. Trusted host
code and the backing repository are outside the untrusted principal boundary;
untrusted code must not receive Python object access, Git/filesystem access or
bootstrap configuration. This module does not implement transport authentication,
grant administration, deployed OS isolation or full policy evaluation.

## Persistence and publication

| Path | Canonical content |
| --- | --- |
| `knowledge/node/<id>.md` | Exact UTF-8 Markdown body, including CRLF/decomposed Unicode |
| `knowledge/node/<id>.yaml` | Canonical Node metadata; body reassembled from its Markdown record |
| `knowledge/{cluster,membership,node_revision,node_type_definition,relation,relation_type_definition}/<id>.yaml` | Generated record's canonical JSON wire value, encoded as the strict JSON subset of YAML |
| `control/metadata.json` | Trusted registered local metadata schemas |
| `control/generation.json` | Existing GenerationRef shape: instance, logical generation UUID, content digest |
| `control/{receipts,requests}/<scope-hash>.json` | Generated CommittedReceipt and original validated BatchRequest |

Managed YAML intentionally accepts only the JSON subset. Duplicate keys, executable
tags, aliases, implicit YAML typing, nonfinite numbers and invalid canonical metadata
reject. Node Properties remain flat; complex system metadata is in the managed
sidecar. This is not a general Obsidian frontmatter importer. Filenames contain
stable IDs, not titles; no title/path reconciliation or raw editor promotion occurs.

The generation digest binds paths and hashes of knowledge/configuration bytes.
It excludes its own descriptor and receipt/request files to avoid circular hashes.
Those files are committed in the same Git tree and validated together; the Git commit
binds the full tree. A generation UUID and entity revision UUID are independent of
Git hashes. Node RevisionRef/NodeRevision are stored canonically; the existing
Relation contract has a numeric revision, so its independent RevisionRef is retained
in its immutable successful receipt rather than a fabricated RelationRevision DTO.

The adapter uses explicit `git -C` plumbing and an isolated temporary index. It
ignores inherited Git environment overrides, stages only constructed bytes, creates
blobs/tree/commit with the prior accepted commit as parent, and publishes using one
`update-ref <ref> <candidate> <expected-old>` call. Prepared objects are invisible
until that succeeds. An OS advisory writer lock in the backing Git common directory
serializes cooperating writers and is released on process termination. Independent
repositories have independent locks; multiple managed refs in one repository share
the writer lock. CAS also catches noncooperating ref writers.

## Retry and recovery

Keep the exact original payload **and expected generation** when retrying. Successful
receipts and requests are retained indefinitely for this M1 development scope, pending
O3. Batch keys scope instance, authenticated principal, `batch.submit` and version.
Single-operation wrappers additionally scope the original operation/version/key.
Payload digests bind normalized JSON including operation order and preconditions.

An exact retry checks current authorization and returns the original committed
receipt before considering the old expected generation. Changed payload with the
same scoped key conflicts. Child operation keys cannot be reused in another batch
to obtain partial replay: that whole new batch conflicts. The original validated
request permits restart verification of digest, key scope and result bindings.

Failure before ref publication has no accepted effects. Failure after publication
may return `REPAIR_REQUIRED` because the caller's result is uncertain; exact retry
finds the committed receipt and does not publish again. Reads/restarts validate
record shapes, paths, generation digest, membership/endpoints, revision/content
bindings and receipt/request/resource consistency. Corrupt or missing required
committed objects fail closed. No reset or automatic repair discards evidence.

## Validation and limits

`tests/test_core_m1.py` uses fabricated disposable real Git repositories. Coverage
includes atomic two-Node/one-Relation admission, denied/invalid final operations,
CAS and competing publication, replay/restart, failures on both sides of publication,
unpublished objects, missing blobs, corruption, isolated instances, strict encoding,
Unicode bodies, generated-model revalidation and an independent Ajv check of actual
Core outputs. The existing contract corpus and generation/distribution checks remain.
Execution counts are recorded in [the implementation report](m1-validation.md).

This establishes logical atomicity and process-level recovery with intact Git
storage. It does not certify power-loss/fsync durability, hostile same-process code,
hardware faults, physical deployment isolation, general YAML authoring, scalable
querying or receipt retention/erasure. Full committed-state and receipt scans are
deliberate for a small M1 corpus. No hosted CI result is claimed locally.

O1 synchronization, O2 approval selection, O3 retention/revocation and O4 multi-cluster
composition still require Owner decisions before extending those behaviors. M1
introduces no new Owner policy decision. The next bounded slice should add an
explicit authorized Node update with immutable revision/CAS tests, followed by
reconciliation only after O1's handoff requirements are settled.

## Historical M1.2 boundary additions and limits

The unreleased canonical baseline now includes immutable RelationRevision snapshots and exact Node/Relation revision-read requests, but M1 neither persists RelationRevision records nor dispatches historical reads. Unsupported record kinds remain fail-closed. Current create-only receipt verification still compares effects against current heads/admission; this is correct while all updates are unsupported. M2 must switch to retained original immutable effect/admission resolution before mutation. See [gaps](../contracts/contract-gaps.md) and [compatibility](../contracts/compatibility.md).

## Current M2.1 extension

M2.1 now persists RelationRevision, requires exact new Node snapshots, and verifies
receipts against original committed effects/admission rather than current heads.
Its canonical HistoryBaseline marks fresh/migrated profiles. Explicit trusted-host
inventory/backfill preserves legacy revision/request/receipt bytes and adds only
proven supplements/missing Relation snapshots. The persistence table above describes
the older M1 subset: current state also permits `knowledge/relation_revision`,
`knowledge/node_revision_snapshot` and `control/history.json`. The older current-head
receipt and absent Relation persistence statements are historical, superseded by
[M2.1](m2-1-immutable-history.md). Public operations remain create/read only.
