# Core contracts specification

Status: proposed implementation baseline, with task-mandated principles recorded in [ADRs](decisions/README.md). Examples are not production schemas. Decisions marked Qxx remain open in the [register](open-questions.md).

Historical design specification. [Production 1.0.0 structural contracts](../contracts/README.md) implement the later domain/Phase 1.1 corrections: standalone Relations, passive Core, authenticated MCP-only agent ingress and explicit unresolved O1–O4. Embedded edges, Core Context and fixed Stable permissions below are superseded as recorded in the [reconciliation register](reconciliation-register.md). Production operations/schema references are mapped in [contract obligations](../contracts/operations.md).

## 1. Boundaries and authority

The Knowledge Plane owns managed Markdown/YAML nodes, embedded typed relations, cluster manifests, membership manifests, immutable provenance, and knowledge revision references. The Control Plane owns desired configuration, principals, grants, policy versions, approvals, and permitted transitions. The Execution Plane owns application services, runs, attempts, checkpoints, and operation events. The Integration Plane owns translation at the edges and implementations of outbound ports.

Dependencies point inward: inbound adapters → application interfaces → domain rules and outbound ports. Outbound adapter implementations depend on those ports; domain code never imports HTTP, MCP, CLI, Git commands, Obsidian APIs, or model SDKs. Application services read policy snapshots from Control and knowledge snapshots from Knowledge, then coordinate explicit mutations. Execution cannot redefine policy or modify canonical files through an unguarded path. Knowledge types do not depend on run types. Control may reference knowledge IDs as scope, never mutate knowledge as an authorization side effect. Integration configuration is desired state in Control; its serializable descriptor types form the Integration contract family.

These are modules in one local process initially. A plane is not a service or database deployment requirement. There is no universal Global State object and no requirement for event sourcing.

| Contract category | Authoritative source | Derived artifacts |
|---|---|---|
| Structural wire data | Versioned JSON Schema 2020-12 resources | Python/Pydantic and TS types; validator registrations |
| Business semantics and operation obligations | This specification, operation tables, and executable conformance cases | Python application interfaces implement them; adapter documentation links them |
| HTTP binding | Optional OpenAPI 3.1 document referencing canonical schemas | HTTP docs/clients only; never domain models regenerated back into schemas |
| Managed knowledge | Markdown body + restricted YAML frontmatter; cluster/membership YAML; provenance records | Search/graph/context caches and Obsidian display |
| Desired access/configuration | Versioned control manifests; secret references only | Effective policy caches |
| Runs/audit/idempotency journal | Local durable execution/control store | Progress display and analytics |

## 2. Shared rules and primitives

In the entity tables, **R** lists required fields, **O** optional fields. All mutable aggregates use header **H**: `id`, `schema_version`, `revision`, `created_at`, `updated_at`. H IDs/creation time are immutable; successful mutations increment revision and update time. Append-only records use **I**: `id`, `schema_version`, `recorded_at`; every field is immutable. Definition revisions are immutable snapshots, selected by an explicitly mutable active reference. Optional means absent is permitted; it does not imply null. Every field is structurally typed in the eventual schema. Rules beyond shape belong in application validation.

| Primitive | Proposed contract and validation | Evolution/compatibility risk |
|---|---|---|
| Entity ID | Lowercase UUID v4 string; workspace scope carried separately; no title/path meaning. References use `{workspace_id, entity_id}` across workspaces, local ID within one workspace | Never reassign IDs. Imported foreign IDs stay in SourceReference; cross-workspace merge is deferred |
| Workspace ID | Independent UUID v4; supplied by consumer configuration; every request context is bound to one | Copying a vault must explicitly choose clone/restore versus fork identity |
| Schema version | SemVer string such as `1.0.0`; full immutable `$id` resource URI is in registry and contract reference | A version field alone cannot identify entity family; `kind`/operation position must do so |
| Entity revision | Positive integer ≤ 9,007,199,254,740,991; per aggregate; CAS expected revision required for writes | Not Git hash, timestamp, or global counter; never reset on migration |
| Timestamp | RFC 3339 date-time restricted to UTC `Z`, seconds or 1–6 fractional digits, four-digit year; no leap seconds; compare instants | Format validators differ. Shared fixture corpus enforces this narrower profile |
| Principal | `{principal_id, kind: human|agent|service, issuer}`; stable local registered ID | Verified request context adds actor/on-behalf-of/session/grant chain. Caller JSON cannot self-assert identity |
| SourceReference | `{source_id, locator}`; optional source entity/message/node IDs, byte hash and media type. Locator is data, not automatically dereferenced | External IDs can change; keep exact source revision/hash and unresolved state |
| ProvenanceReference | `{record_id}` resolving immutable source/derivation record; revision-specific when citing knowledge | Provenance access is independently authorized; citations must not leak private titles |
| Error | `{code, message, retryable, correlation_id}`; O `field_errors` with JSON Pointer, `retry_after_ms`, sanitized `details` | Stable code vocabulary; messages not machine parsed. HTTP status/JSON-RPC code live in bindings |
| Capability ID | Namespaced string, e.g. `sb.knowledge.read`; a registry defines meaning, resource scope and version | Capability additions cannot broaden old grants. Discovery is not authorization |

All managed records reject unknown core fields. Deliberate `extensions` is an optional namespaced object with bounded JSON values, e.g. `org.example.review`; it grants no permissions and has no core semantics. Do not use arbitrary JSON blobs to conceal essential contracts. JSON numbers must be finite; integer bounds preserve JS precision. Duplicate JSON keys are invalid at ingress. YAML uses a safe loader restricted to JSON-compatible scalars, string keys, no tags/anchors/aliases, no implicit date objects or duplicate keys. Strings remain strings. No executable Markdown/frontmatter features are evaluated.

Canonical serialization: UTF-8, LF, NFC-normalized identifiers and tag strings, no locale-dependent sorting; body text is preserved without Unicode normalization. Deterministic hashes use specified input bytes or a specifically versioned normalized operation payload, never unspecified YAML reserialization. Requests use full replacement payloads in MVP; generic JSON Patch is deferred.

## 3. Knowledge family

Foundational means required before managed knowledge writes (M1–M5), not “generate every schema now.” Only node and cluster schemas are illustrated in this delivery.

| Entity / responsibility / stage | Identity, lifecycle, fields | Relationships and mutation ownership | Structural vs semantic checks; evolution risk |
|---|---|---|---|
| Knowledge Node — curated unit; foundation | H. R `kind`, `title`, `body`, `lifecycle`, `sensitivity`, `provenance_refs`, `relations`. O `topics`, `aliases`, `extensions`. Draft → active → deprecated → archived | App owns changes; ID/created immutable; content/classification mutable with CAS. References provenance and nodes. Body is Markdown, frontmatter holds all other fields | Schema checks bounds/enums; app checks sources, targets, access, timestamps, transitions. Title/path changes never change identity. New kind/state enum is a compatibility decision |
| Relation — typed assertion, embedded in source node; foundation | R `id`, `type`, `target_id`. O `provenance_refs`, `confidence`, `valid_from`, `valid_until`. Relation ID stable within workspace, retired on removal | Source node revision owns full edge set; no separately mutable edge store. Target reference and predicate catalog required | App checks permitted source/target kinds, validity interval, duplicates and predicate rules. Directed edges by default; symmetric retrieval is a derived view only for predicates explicitly designated symmetric. Never infer symmetry from “symmetric-ish” |
| Cluster — knowledge scope, not folder; foundation | H. R `name`, `class` (`shared_stable`, `shared_stack`, `private_memory`, `session`, `additional`), `owner_principal_id`, `sensitivity`. O `expires_at`, `description` | Classification/owner changes privileged; class immutable for MVP, create new cluster instead. Manifest references membership aggregate by cluster ID | Schema checks fields; app enforces expiry for session, owner registration, permitted classes. Cluster membership does not itself grant reads. Adding classes breaks old consumers |
| Cluster membership — inclusion manifest; foundation | H with `id` equal cluster ID. R `cluster_id`, `members` list of `{node_id, added_at, added_by}`. O per-entry `expires_at`, `approved_node_revision`, `approval_ref`; last two required for Stable | Cluster aggregate owns manifest revision. Membership entry identity `(cluster_id,node_id)`; changes CAS manifest, not node | App checks existence, uniqueness, lifecycle, sensitivity and promotion gates; expired memberships excluded. Stable reads the stored approved revision independently of the editable candidate; current policy and historic-byte integrity still apply (proposal under Q03). Separate manifest avoids node/cluster dual writes. Large-cluster partitioning deferred |
| Knowledge lifecycle — finite state vocabulary/rules, not generic entity; foundation | Versioned allowed transitions; node field `lifecycle`. No separate UUID | Application changes node state with expected revision and reason; immutable audit records carry transition evidence | JSON enum only proves state spelling; app proves transition/approval. Import DROP/ARCHIVE/EXTRACT/PROMOTE are triage dispositions, not node lifecycle values |
| Source/provenance record — evidence and derivation; foundation | I. R `source_kind`, `source_ref`, `content_hash`, `availability`, `origin`. O `parent_provenance_ids`, `tool_version`, `model_ref`, `transform`, `reviewer`, `license` | Append-only; source may be local artifact, human assertion or derived node revision. `origin` human/imported/ai_derived; no claim that model output is verified | App verifies hashes where bytes available, acyclic derivation references, independent access and recorded uncertainty. Missing bytes remain `unavailable`; mutable availability updates use a new record. Privacy erasure exception requires tombstone/reason, see Q06 |
| Knowledge revision — immutable revision locator; foundation | R `entity_id`, `revision`, `schema_version`, `content_hash`, `recorded_at`, `actor_id`; O `git_commit`, `previous_revision`, `provenance_refs` | Key `(entity_id,revision)`; created on canonical commit. Git blob/commit and journal locate full historic content, no duplicate body store | App verifies content hash and monotonic linkage. Git commit alone cannot represent entity revision. Rewriting Git history invalidates locators; managed branch disallows force rewrites |

The node schema's `body` is the in-memory/wire projection of the Markdown body. It is not duplicated in frontmatter. Embedded `relations` preserve the existing vault convention; the read graph is rebuilt from them. Legacy wikilinks are display aliases until a resolver explicitly maps them to IDs, with ambiguity reported rather than guessed. The project relation catalog remains local desired configuration; shared package defines predicate structure and minimum known semantics, not every user's ontology.

## 4. Execution family

| Entity / responsibility / stage | Identity, lifecycle, fields | Relationships and mutable properties | Validation and compatibility |
|---|---|---|---|
| Operation definition — named application behavior; foundation | Immutable `(operation_id, contract_version)`; R input/output/error schema references, capability requirements, effect class, mode, concurrency/idempotency/cancellation/audit semantics | Ordinary docs + Python interface + conformance tests, not a new descriptor language. Catalog/discovery is a generated or explicitly checked projection | App/CI checks referenced schemas and behavior coverage. Semantic changes require contract version even if shape unchanged |
| Process definition — versioned single-purpose multi-step procedure; defer M7 | I plus R `process_key`, `version`, `input_ref`, `output_ref`, `step_operation_ids`, `timeout`, `retry_policy`; O checkpoint policy | Immutable approved definition; runs pin version/hash. Initially ordinary Python composition, no user-supplied code in records | Validate operation existence, bounded retries, permissions. Do not store Python source in a contract. Generic process description schema is deferred |
| Workflow definition — composition of processes; defer M8 | I plus R `workflow_key`, `version`, `steps`, `dependencies`, `failure_policy`; O explicit compensation references | Immutable version; runs pin it. Optional acyclic static composition, not a general scheduler | App validates DAG, type-compatible edges and bounded fan-out. | Run — durable invocation status; defer M6 | H. R `operation_id`, `contract_version`, `principal_id`, `status`, `input_ref`, `attempt`, `policy_snapshot_ref`. O parent run, deadline, checkpoint/result/error refs, cancel request time | Execution owns queued/running/succeeded/failed/cancelled/indeterminate state; immutable identity/input/principal/definition refs | Transactional state transition/CAS and attempt fencing. Terminal outcome immutable. Cancellation request is separate from final status |
| Event — fact about operation/run; defer M6 | I. R `run_id`, `sequence`, `event_type`, `payload_ref`; O causation/correlation ID | Append-only per-run ordered stream; stream cursor not universal global order. | Checkpoint — recoverable process progress; defer M7 | I. R `run_id`, `attempt`, `step_id`, `state_ref`, `state_schema_ref`, `definition_hash`; O previous checkpoint | Immutable, exact process version; payload local durable store | App proves committed step and restart compatibility; no secrets or arbitrary deserialization. | Execution result — final typed outcome; defer M6 | I. ## 7. Behavioral contract

Each Bxx requirement needs a conformance case at the milestone that implements it. Recommendations use SHOULD; open decisions cite Qxx.

| ID | Normative requirement | Observable rejection/recovery |
|---|---|---|
| B01 Lifecycle | Creation starts draft. Draft→active requires source/provenance and required review; active→deprecated requires reason; deprecated→active requires fresh review; draft/active/deprecated→archived requires reason. Archived→draft requires restore approval. No implicit hard delete | `invalid_transition` / `approval_required`; no write |
| B02 Stable/Stack | Shared Stack may contain reviewed or draft candidates, clearly labeled. Stable membership requires active node, verified provenance for asserted claims, explicit human approval of exact content/revisions, and target sensitivity policy. AI confidence alone is insufficient | Promotion adds Stable membership; removal from Stack is explicit. Revised proposal: Stable reads the approved immutable revision while edits create a separate candidate; only approval/CAS replaces its pointer. Current access restrictions apply to historical content. See stable-revisions.md; Q03 remains open |
| B03 Membership | Add/remove uses expected manifest revision, existing node and cluster, permitted owner/scope, no duplicates. Session expiry is enforced on reads even if cleanup is delayed | `revision_conflict`, `not_found` or concealed `not_found`; membership never declassifies content |
| B04 Access | Every application entry authenticates principal context and checks capability + resource scope + sensitivity + session binding + policy. All filters apply before counts/snippets/graph traversal/context output | Default deny. Deny wins across all memberships; a public cluster does not override a private node or private relation target |
| B05 Concurrency | All mutations compare expected aggregate revision and canonical content hash under workspace writer lock. External/manual edits invalidate the loaded snapshot; never overwrite them automatically | `revision_conflict` with no sensitive current content. Client rereads and explicitly reapplies change |
| B06 Idempotency | Mutation key bound to workspace, verified principal, operation/version and normalized payload digest. Commit effect and replay result together. Same key/different payload is conflict; concurrent same key has one winner | Replay still requires current read permission; revoked principal gets deny. MVP retention proposed 30 days (Q08); clients must not retry beyond advertised window |
| B07 Integrity | Targets and provenance refs must resolve in the configured workspace snapshot or carry explicit unavailable/external evidence status. Canonical relations cannot silently point to unknown internal IDs | Missing refs reject writes; legacy/unmanaged broken links remain diagnostic source data. Deletion restricted to tombstones; incoming edges visible in authorized diagnostics |
| B08 Provenance | Derivation records retain original IDs, source hashes, message locators, tool version and human/AI origin. Promotion preserves provenance. Raw content retention is separate policy | Inaccessible sources yield redacted citation handles, not authorization bypass. Erasure requires Q06 policy; no automatic purge in MVP |
| B09 Ownership | Each field/aggregate has one writer path. Graph/index cannot write canonical files. Git changes outside the app are human input requiring reconciliation | Drift quarantines affected managed records until validation/revision reconciliation; no silent adoption |
| B10 Runs | Cancellation is best effort at safe points; committed effects remain committed. Terminal result cannot be overwritten by a late attempt. Attempts carry fencing token; retries are bounded and only for declared safe failures | Unknown remote effect → indeterminate, reconcile before retry. Request cancellation ≠ run cancelled |
| B11 Errors | Distinguish validation/authentication/authorization/not-found/conflict/invalid-transition/unsupported-version/deadline/cancelled/transient/integrity/internal/indeterminate codes. Only transient failures of safe/idempotent steps are automatically retryable | Sanitized stable error envelope; no automatic retry for denied, invalid, conflict, or unknown effect |
| B12 Atomicity | MVP command commits one aggregate plus its provenance/audit/idempotency journal records as one recoverable local transaction. Readers see old or new committed state, never prepared writes. Multi-aggregate effects require explicit staged procedure and recovery record | See transaction protocol below; Git alone does not provide a filesystem/database transaction |
| B13 Context | Compile authorized snapshot at explicit revisions, policy/config version, cluster attachment set and fixed budget. Sort by explicit priority then ID; deterministic truncation and encoding/tokenizer version. Record manifest/hash and excluded reasons without revealing denied data | Same snapshot/options/tokenizer yields same bytes. Revocation is rechecked before delivery; no vector/LLM ranking in deterministic MVP |

Cluster attachment belongs to the process/session's authorized context request, not node ownership or a permanent grant. An agent's private-memory cluster and a session cluster have distinct owners/expiry; only explicit approved operations may copy knowledge into shared spaces. “Shared” means shared among authorized principals, never internet-public.

Sensitivity order is `public < internal < personal < sensitive < secret`. An operation must satisfy explicit capability/resource grants and its allowed sensitivity ceiling; explicit deny always wins. Effective output sensitivity is at least the maximum of included node, selected cluster and disclosed provenance/target material. Merely referencing a restricted target does not authorize reading it: omit/redact that reference as required by policy. Counts and diagnostics must not reveal its existence. A caller may not lower sensitivity through ordinary replacement; declassification needs a separate reviewed administrative operation, deferred from MVP.

Server-owned IDs/revisions/timestamps are allocated or verified by the application; clients cannot replace them as editable content. The application takes time from an injected clock and validates updated_at ≥ created_at. Cluster `description` is an explicitly nullable display field: omission or null means no description. Other optional fields do not acquire implicit nullability.

### Proposed local transaction protocol (M3 gate)

Use a single managed writer per workspace. Under lock, verify on-disk hashes and expected revisions; stage complete replacement files in the same filesystem. Persist a durable journal intent containing before/after hashes, staged paths, audit intent and idempotency key. Flush files and journal; publish replacements, create the managed Git commit, and durably mark journal committed with result/audit completion. Application readers are fenced while a transaction is prepared. Index refresh follows commit and can be retried. A failed Git commit is an incomplete transaction, not a successful write.

On restart before serving reads/writes, inspect prepared transactions: roll forward if all expected after-images are available and no external divergence occurred; otherwise restore verified before-images, or stop in repair-required mode if neither is safe. Never claim atomic visibility to an external editor during a multi-file publish. Keep normal commands to one knowledge aggregate; immutable provenance additions are part of the recoverable batch. Approval consumption and membership changes must be coordinated in the same journal transaction. Durable audit events describe recovery outcome even after rollback.

This is a specified recovery obligation, not a proven implementation. M3 must test Windows replace/locking/flush behavior, Git hooks and concurrent editor changes. If that protocol cannot meet the requirement, narrow the mutation boundary or seek an explicit storage decision (Q04); do not quietly introduce a second canonical database.

## 8. State ownership and recovery

| State | Owner / persistence | Recovery and authority |
|---|---|---|
| Canonical persistent knowledge | Knowledge repository; Markdown/YAML and referenced immutable source records, Git history and backup | Restore files/history and validate; rebuild derived stores. Git is version history, not a backup by itself |
| Desired configuration | Control manifests, policy versions, grant/approval records; secrets external | Validate before activation; fail closed if unavailable. Revocation must survive restart |
| Runtime execution | Execution durable run/attempt/checkpoint/result/idempotency journal; SQLite proposed | Resume only from compatible checkpoints and verified effects. Never reconstruct permissions from logs |
| Derived indexes/caches | Index adapter; rebuildable graph/search/context caches with source/config hash | Delete/rebuild; stale index must not widen access. Query candidates rechecked against current policy and source revision |
| Temporary session state | Session owner; bounded TTL, scoped cluster attachments, transient scratch | Expire by clock on access. Crash may discard uncommitted scratch; explicit promote is required for durability |

## 9. Versioning, migrations and compatibility

Schema version describes data meaning/shape; entity revision describes one object's changes; API/binding version describes transport mapping; runtime version describes implementation release. Operation contract version also covers behavioral obligations. They evolve independently, with an explicit tested compatibility matrix.

Every released schema `$id` is immutable and contains exact SemVer. No network retrieval at validation time. Schema bundles and generated artifacts carry content hashes and package release version. During 0.x every minor may break; production uses 1.x rules. Documentation-only annotation changes may be patch; even patch releases get new immutable IDs. Changes that accept/reject different values or alter meanings require a reviewed compatibility classification, never a cosmetic patch.

For producer P and consumer C, compatibility means P's possible outputs remain accepted and correctly interpreted by C, and C's requests remain accepted by P. Adding an optional property to a closed schema is NOT automatically backward compatible: an old reader rejects the new producer. Enum expansion, nullability, default changes, constraints, unknown-property behavior and error/operation semantics require directional tests. Permit additive optional features only through negotiated schema versions or already-defined namespaced extension slots; never “ignore unknown” for policy.

Migrations are explicit offline commands with source/target versions, dry-run manifest, hashes, fixtures, expected revisions, backup and resumable journal. Preserve IDs, provenance and history; increment affected revisions. No implicit migration during ordinary reads. New runtime must read old supported versions or provide an explicit migration; it cannot silently rewrite a vault. Keep previous release/schema resources for at least two supported minor releases (recommended initial policy; Q09).

Before migration, verify Git working state and backup; validate after migration, then rebuild indexes/generated artifacts. Rollback restores the complete pre-migration snapshot and compatible runtime/config, not just the old code. Do not roll back across new writes without an explicit reverse migration or restore procedure. Audit evidence of attempted migration survives. Release gates include old/new valid and invalid fixtures, generated-code drift, cross-language parity, behavioral regression cases and a human review of semantic changes. [Toolchain](contract-toolchain-spec.md) defines limitations of automated compatibility analysis.
