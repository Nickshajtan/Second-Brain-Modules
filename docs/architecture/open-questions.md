# Open questions and decision register

These are visible implementation gates, not requests to stop architecture delivery. Proposed defaults allow the first fixture spike to proceed with synthetic data. A reviewer must resolve each gate before enabling the affected production behavior.

| ID / owner | Decision needed | Proposed default / alternatives | Gate and deciding evidence |
|---|---|---|---|
| Q01 / repository owner | Public schema URI namespace, repository name, license and package names | Repository identity Second-Brain-Modules and MIT license are established. Production schema namespace and package names remain open; examples use `example.invalid` | Before M1 production schemas/publication; verify ownership, desired redistribution/license and name availability |
| Q02 / knowledge owner | Managed-note adoption and source retention | Explicit opt-in, lightweight unmanaged notes remain; import candidates only, no mandatory transcript vault | Before M4 adoption/M9 apply; review representative notes and actual retention needs |
| Q03 / knowledge owner | Stable/Stack and relation semantics | Recommend an approved-revision Stable pointer independent of candidate edits; promotion replaces the pointer after approval. Review historical relation resolution/current policy in stable-revisions.md. Existing predicate names retained, ambiguous meanings clarified | Before M5; small curated example set and intended symmetry/cardinality decisions |
| Q04 / implementer + owner | Local commit/recovery protocol and storage backend | Markdown/YAML authority + single writer + durable journal + managed Git commits; SQLite execution/derived stores. Alternative: explicitly revise authority model if atomicity cannot be met | Before M3 accepted; crash/flush/locking tests on all OS, concurrent Obsidian edit tests |
| Q05 / owner | Principal registration, delegation and human approval identity | Explicit local profiles, no implicit admin, human-only Stable approvals; no self-approval where policy requires separation | Before M3 writes/M5 promotion; actual local/harness account model |
| Q06 / owner | Provenance erasure, audit retention and sensitive backups | No automatic deletion; tombstones/redacted metadata under reviewed retention policy; never promise unconditional immutable retention for secrets | Before destructive migration/deletion or production audit retention; personal retention requirements |
| Q07 / deployment owner | Trust against malicious same-OS-user code | Application policy protects cooperative clients; untrusted agents receive scoped context/read-only access or separate OS identity | Before agent file access; concrete deployment threat model, Windows ACL feasibility |
| Q08 / implementer + owner | Idempotency lifetime and journal/audit quotas | Advertise 30-day retry window initially; old keys not safe to replay afterward; results redacted after revocation | Before M4 production mutations; backup/retry horizon and disk budget |
| Q09 / maintainer | Supported schema versions/deprecation window | Current + previous two supported minor releases; explicit migrations, no implicit rewrite | Before first stable release; number of consumers and upgrade cadence |
| Q10 / adapter maintainer | MCP profile/SDK and legacy client support | Inspect dated 2026-07-28 profile; select stable SDK/client combination by actual integration tests; no handwritten compatibility translator | Before MCP adapter implementation; target clients, SDK released support and cancellation/lifecycle fixture matrix |
| Q11 / owner | First remote consumer/auth deployment | Disabled by default. Choose REST or MCP HTTP for a concrete consumer, not both for completeness | Before M11; user need, auth provider, network topology and security tests |
| Q12 / context consumer | Budget accounting and deterministic ordering details | Explicit priority then ID, UTF-8 output, pinned tokenizer if token budget; byte budget supported without provider dependency | Before M10; representative context fixtures and selected harness constraints |
| Q13 / maintainer | Candidate generator release compatibility and exact locks | Locks, local Windows generation/parity and CI definitions now exist. Advanced features, hosted cross-platform proof and production schema support remain open; replace incompatible tools via ADR | Before generated package release; actual Python/TS fixtures, all-OS determinism and offline ref proof |
| Q14 / workspace owner | Workspace fork/restore identity and timestamp import rules | Restore preserves workspace ID; independent fork allocates a new one and retains lineage; imported observation time is separate from managed creation time | Before copy/fork tooling; collision and provenance fixtures |

Decisions already required by the task: canonical JSON Schema 2020-12, Python core/TS support, generated models, transport-independent boundary, optional OpenAPI HTTP binding, separate state authorities, modular monolith. New details such as UUID format, SQLite use, stable membership gates and retention windows are recommendations. The [ADRs](decisions/README.md) distinguish these explicitly.
